## 1. 执行摘要

**总体结论：RBAC 改造的骨架质量高于同类毕设水准——数据模型、鉴权装载链路、三层（Gateway/print/各服务）独立校验、前端权限收敛均落地完整，权限点在代码、SQL 种子、方案文档、前端路由四处完全一致；但当前存在 8 项 P1 级缺陷需要在生产部署 / 论文演示前修复，核心风险集中在「订单状态机缺乏数据库层原子性保障」「RBAC 双源权威语义分裂」「管理员更新可清空角色导致账户锁死」「前端契约错误把失败当成功」四个主题。**

问题统计（去重合并后）：

| 级别 | 数量 | 说明 |
|---|---|---|
| P0（越权/资损/数据损坏） | 0 | 默认种子授权矩阵下未发现可直接利用的越权 |
| P1（重要缺陷，上线前必须修复） | 8 | 见 §2 表 F-01 ~ F-08 |
| P2（一般问题，上线前建议处理） | 22 | 见 §2 表 F-09 ~ F-30 |
| P3（改进建议） | 13 | 见 §2 表 F-31 ~ F-43 |

**对「逻辑设计与事务处理是否足够稳健」的直接回答**：

- **事务层面**：全项目仅 5 处 `@Transactional`（`AdminServiceImpl.register/update/delete`、`AccountServiceImpl.registerUser/bindQqEmail`），恰好完整覆盖了 RBAC 双写（`user_account.role` + `sys_user_role`）的全部主链路，事务内无邮件/Redis/文件 IO 副作用，回滚语义正确——这部分是稳健的。**唯一的多表一致性缺口是用户删除**（不清理 `sys_user_role`/订单/文件，无事务）。**最大的稳健性缺口不在事务注解，而在数据库层原子性**：订单状态机是「读-内存判定-无条件 UPDATE」模式，无乐观锁、无 `WHERE order_status=当前状态` 守卫，并发下可越级/互踩；排队号生成同样存在竞态且无唯一约束兜底。
- **逻辑设计层面**：订单金额后端重算、状态机白名单流转、文件上传多层校验链、验证码原子删除等核心设计是正确的；但 RBAC 存在「双源权威」设计缺陷——`user_account.role` 字段与 `v_account_perms` 视图两套判定源并存且不一致时代码不自洽，superadmin 直通以 role 字段为准导致「DB 停用超管」这一运营动作在三端语义分裂。
- **运营前置约束**：Phase 5 数据权限未落地前，**operator 角色实际可读取全平台订单、文件与用户资料**，不建议向真实门店发放 operator 账号。

## 3. 分域审查详情

### 3.1 RBAC 权限改造专项

**落地完整性（通过）**：print-service 22 处 `requirePermission` 检查点与 007 种子 25 个权限点、方案文档清单、前端 `meta.permission` 逐点比对**完全一致**，未发现拼写不一致或漏加鉴权的写接口；chat-service 17 个管理端接口全部走 `require_permission` 且权限点与种子一致（`main.py:177-388`）；operator 默认未授予 admin/user/store/service 管理类权限。

**核心设计问题**：
1. **双源权威语义分裂**（F-04/F-12）：`requireAdmin` 走 `user_account.role` 字段链，`requirePermission` 走 `v_account_perms` 视图链，superadmin 直通只认字段不认 DB 角色状态。这与方案 §4.5 参照的若依模型（基于权限集合含 `*:*:*` 的集合判定）不同，是实现与方案的实质偏差。
2. **权限装载容量隐患**（F-05）：GROUP_CONCAT 静默截断是安全相关的失败模式（fail-closed 但整体权限丢失）。
3. **双写静默半失败**（F-11）：`syncUserRole` 查不到 roleId 时静默跳过，无日志、不回滚。
4. **前端拦截面**（F-06/F-27）：403 被当成会话失效处理，权限缓存无失效机制。
5. **数据权限预留未实现**（F-09）：`data_scope` 字段与方案 §4.6 承诺的 operator↔门店过滤均未落地，operator 当前可读全平台数据。

**正面结论**：权限装载合并进 `AuthInterceptor` 既有的一次查库（`selectWithPermsById`），未增加每请求 SQL 次数；角色变更后旧 token 立即失效（每请求回库比对 role，不匹配即 401）；chat-service「连接失败→503、查询为空→403」的 fail-closed 区分正确，且 superadmin 一并 fail-closed；Gateway 与 print-service 公开白名单逐条一致且做了 `/api/print` 前缀归一化（`GatewaySecurityFilter.java:142-180` vs `AuthInterceptor.java:54-80`）；JWT claim 校验规则（60s 偏移、jti UUID、sub 格式、role/username 非空、拒绝 alg=none）在 Gateway/print/chat/schedule 四端实现一致。

### 3.2 认证与会话

**通过项**：图形验证码 Redis `getAndDelete` 原子一次性（`LoginCaptchaService.java:64`）；邮箱验证码 Lua「比对即删」原子、按 purpose 隔离、Redis 仅存 HMAC 盲索引哈希、60s 冷却 `setIfAbsent` 原子、单邮箱 20/天（`QqMailVerificationService.java:21-142`）；注册/找回强制先验邮箱验证码，账号不存在时返回与验证码错误一致的模糊文案防枚举；密码策略（8-72 位、无空白、两类字符）全路径一致，BCrypt 登录前校验 `$2a/b/y$` 前缀；禁用/改角色账户下一请求即失效。

**问题**：F-08（改密后旧 token 有效）、F-29（锁定单机内存态 + 锁定 DoS）、F-31（并发注册 500）。

### 3.3 订单核心业务

**通过项**：金额后端按 `DB单价 × 页数 × 份数` 重算并完全忽略客户端 totalPrice（`OrderInfoServiceImpl.java:155-161`）；copies 1-99、pageCount 1-500 全量白名单校验；新订单强制状态 0；终态 3/4 不可再流转；用户只能查看/取消自己的订单；admin 建单也走完整价格重算与校验。

**问题**：F-01（状态机非原子，**并发专项最大缺口**）、F-02（1→4 取消边 + TOCTOU）、F-19（取件码纯装饰）、F-20（排队号竞态无唯一约束）、F-26（先审计后落库 + 0 行伪成功）、F-32（double 落库/弱随机）。

### 3.4 文件业务

**通过项**：下载/详情/按订单列举全部经 `requireFileAccess → requireOrderAccess` 属主校验（横向越权 403）；存储路径强制 `/files/<单段文件名>`，拒绝 `..`、`\`、`:`、`\0`，落盘名服务端 UUID；上传链完整（扩展名→magic bytes→PDF 深度结构→OOXML 防炸弹/宏/ActiveX→图片尺寸像素→内容审核→ClamAV）；元数据写失败补偿删除物理文件；OCR 下载 token 白名单 + 目录前缀校验无穿越。

**问题**：F-18（扫描/审核默认 fail-open）、F-33（删除顺序）、F-34（无配额）、F-30b（游离权限点体系）。

### 3.5 事务处理专项（回应核心问题）

全局 `@Transactional` 共 5 处：`AdminServiceImpl.register/update/delete`（:51,83,105）、`AccountServiceImpl.registerUser/bindQqEmail`（:29,86）。

| 写路径 | 事务 | 结论 |
|---|---|---|
| 管理员注册/更新/删除（user_account + sys_user_role 双写） | 有 | 覆盖完整，回滚正确 |
| 用户注册/绑定邮箱 | 有 | 覆盖完整 |
| **用户删除（user_account 单表 + 应清理的 sys_user_role/订单/文件）** | **无且清理缺失** | **F-10，全项目唯一多表一致性缺口** |
| 订单状态更新 | 无需（单表） | 但缺 DB 层原子守卫（F-01），稳健性缺口在并发不在事务 |
| 文件上传（落盘 + 插库） | 补偿模式 | 失败补偿删除，处理得当，无需事务 |
| Store/ServiceItem CRUD | 单表 | 无需事务 |

事务方法体内均无邮件/Redis/文件 IO 副作用（发信在 controller 层事务外）；未发现 catch 后吞异常导致 DB 写「伪成功」的路径。**结论：事务注解的使用是克制的、正确的；稳健性短板在于数据库层原子性保障（条件更新/唯一约束）而非 Spring 事务覆盖。**

### 3.6 Python 服务

**chat-service（通过为主）**：Agent 工具白名单双重强制（LLM 每轮先查白名单 `agent.py:229-232`，执行器只实现 7 个只读工具 `tools.py:104-149`）；用户身份仅由 JWT principal 注入，工具回源 Gateway 由 print-service 二次鉴权，模型上下文不含 JWT/敏感字段（jwpassword 在工具返回前剔除）；会话/消息/反馈 SQL 级 owner 隔离，删除为归档非物理删；`update_settings` 校验未知工具名。问题：F-14/F-15/F-16/F-30。

### 3.7 前端权限架构与契约

**通过项**：权限判定全部收敛到 Pinia store；AdminList 的 localStorage 角色硬判断清除彻底（残留 localStorage 读取仅为展示与自身 ID 比较，无控制级残留）；`v-permission` 指令移除 DOM 且守卫先行加载权限，时序安全；守卫权限回退链最终收敛（回退目标也无权限则登出，无重定向死循环）；请求拦截自动带 Bearer。

**问题**：F-06（403 登出）、F-07（假成功）、F-27（缓存无失效 + 静默卡死）、F-28（动态菜单偏差）。
