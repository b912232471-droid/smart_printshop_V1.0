# 图文生成功能更新迭代方案（基于图片生成模型能力）

> 版本：v1.0（2026-09-06）
> 定位：`docs/image-generation-development-plan.md` 的上位迭代方案。该手册解决了"模型选型与配置就绪"，本方案回答"围绕生成能力做哪些功能、每个功能怎么落地、上线后基于现有管理体系怎么运营维护"。两文冲突处**以本方案为准**（主要是第 2 节架构决策替代原手册第 3 节部分设计决策）。
> 阅读对象：后续实施开发者。文中类名、接口路径、配置键、SQL 均按现有代码风格编写，可直接照做。

## 1. 背景与目标

### 1.1 现状

- TokenHub 三款文生图模型配置已就绪（`photo-service/app/core/config.py` 的 `IMAGE_API_*` 与 `IMAGE_MODEL_CATALOG`），功能代码未开发：

| 模型 | 价格/张 | 定位 |
|---|---|---|
| `seedream-image-v5.0-lite` | 0.22 | 默认主力，中文文字渲染强，适合海报/手抄报 |
| `hy-image-v3` | 0.20 | 37 组预设尺寸贴合打印纸张比例，支持水印脚注 |
| `seedream-image-v5.0-pro` | 0.30（>261 万像素 0.60） | 旗舰质量档 |

- 平台已有可复用资产：订单闭环（先 `createOrder` 后 `fileApi.upload(orderId)`）、`file_info` + `data/files` 卷、OCR 的 owner-scoped 下载模式、`ImageContentModerationService`（fail-closed）、Redis 客户端模式（验证码/邮件）、RBAC 权限体系（2026-09-06 已落地）、`chat_settings` 运营配置 + 审计模式、chat-service Agent 受控工具机制。

### 1.2 目标

1. 打通"生成 → 存储 → 下单打印 → 取件"完整闭环，把"一站式图文处理"从"用户传文件"升级为"用户创作到实体交付"。
2. 生成能力可运营：功能开关、配额、模板、成本台账、内容审核全部纳入现有管理端与 RBAC 体系。
3. 不破坏既有架构约束：photo-service 保持无状态、不占库、不挂共享卷。

### 1.3 非目标（本期不做）

- 图生图编辑（vidu-image-q2 异步接入，见 6.1/6.2 预留）；
- 去水印、去 logo、真人换脸类编辑（合规红线，永不纳入）；
- 积分/支付体系（配额控制已够毕设场景，见 7.3）。

## 2. 总体架构决策（实施前拍板，替代原手册第 3 节相应决策）

### 2.1 编排层放 print-service，photo-service 只做模型适配器

用户侧生成接口落在 print-service（新 `imagegen` 包，完全镜像现有 `ocr` 包模式），photo-service 仅新增一个"模型调用适配端点"。理由：

1. **AGENTS.md 明确约束**：photo-service 无状态、不占库、生产 `--scale photo-service=3` 多实例。配额计数、生成记录、成本台账都需要共享存储，放 photo-service 就得给它加 Redis/MySQL，破坏该约束。
2. **docker-compose 事实**：`./data/files:/data/files` 卷目前只挂在 print-service（docker-compose.yml:82-83）。生成图落盘复用该卷，photo-service 不需要新挂载。
3. **复用现成安全件**：配额用 print-service 既有的 `StringRedisTemplate` 模式（参照 `LoginCaptchaService`）；内容审核直接调 `ImageContentModerationService`；鉴权用 `AuthContext`/`requirePermission`；响应统一 `ApiResponse`。
4. **闭环天然在 print-service**：生成图转打印订单、`file_info`/`image_gen_record.order_id` 回填都在 print_shop 库。

### 2.2 调用链与鉴权

```
前端(axios) → Gateway /api/print/imagegen/** → print-service /api/imagegen/**
                                                  │ 1. 配额(Redis) 2. prompt 校验/润色
                                                  │ 3. RestTemplate(90s) 调 photo-service
                                                  ▼
                                    photo-service /api/photo/image-generate
                                                  │ 模型白名单 + TokenHub /v1/images/generations
                                                  ▼
                                    返回 b64 → print-service 审核 → 落盘 data/files/imagegen/
                                              → 写 image_gen_record → 返回记录+下载地址
```

- JWT 一路透传：Gateway 校验后，print-service 调 photo-service 时原样携带用户的 `Authorization` 头，photo-service 用既有 `core/security.py` 的 `get_current_user` 依赖校验（同一平台密钥，深度防御，与现有 photo 接口一致）。
- **photo-service 端点不做业务**：不查库、不计数，只做模型 ID 白名单、参数校验、Key 为空抛 503（对齐 `BAIDU_OCR_*` 模式）。

### 2.3 存储决策：落盘共享卷 + 记录表（替代 b64 直传方案）

生成结果由 print-service 写入 `data/files/imagegen/{accountId}/{token}.png`，并写 `image_gen_record`（见第 3 节）。前端拿到的是记录 + `/api/print/imagegen/download/{ownerId}/{token}` 鉴权下载地址，而不是裸 b64。理由：不落盘就没有闭环下单、没有"我的作品"、没有审计与成本核算；OCR 已验证这套 owner+token 模式可行。

### 2.4 超时与熔断（必改项，否则生成必被超时杀掉）

| 层 | 现状 | 改法 |
|---|---|---|
| Gateway print 路由 TimeLimiter | `GATEWAY_PRINT_CB_TIMEOUT` 默认 **10s** | `.env` / `.env.local` 显式设 `GATEWAY_PRINT_CB_TIMEOUT=90s`（生成请求 10-60s，10s 必超时）。该值只是上限，不影响快请求的实际耗时 |
| Gateway photo 路由 TimeLimiter | `GATEWAY_PHOTO_CB_TIMEOUT` 默认 10s | 同步设 90s，为后续前端直连 photo 的场景与 vidu 异步预留 |
| print-service → photo-service 内部调用 | 默认 `RestTemplate` 读超时 20s | `RestTemplateConfig` 新增独立 `imageGenRestTemplate` Bean（connect 5s / read 90s），不动公共 Bean |

### 2.5 模型目录的下发与校验

- photo-service 新增 `GET /api/photo/image-models` 返回 `IMAGE_MODEL_CATALOG`（含 `price_per_image`、尺寸建议），print-service 代理为 `GET /api/imagegen/models`，前端下拉走接口不硬编码（原手册第 4 节要求保留）。
- `model_id` 双重白名单：print-service 校验请求的 model 在 models 接口返回集合内（防任意模型注入），photo-service 端再校验一次（原手册要求，保留）。
- 价格快照：下单成本按调用时刻 catalog 单价写入记录的 `cost_amount`，后续调价不影响历史台账。

### 3.1 生成记录表（print_shop 库）

```sql
CREATE TABLE IF NOT EXISTS `image_gen_record` (
  `id` BIGINT AUTO_INCREMENT PRIMARY KEY,
  `account_id` INT NOT NULL COMMENT '生成者(user_account.id)',
  `token` CHAR(36) NOT NULL COMMENT '下载令牌(UUID)',
  `model_id` VARCHAR(64) NOT NULL COMMENT '模型标识',

  `polished` TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否经过AI润色',
  `template_key` VARCHAR(64) DEFAULT NULL COMMENT '使用的模板标识',
  `file_url` VARCHAR(512) NOT NULL COMMENT '存储路径 /files/imagegen/...',
  `width` INT NOT NULL, `height` INT NOT NULL,
  `size` VARCHAR(32) NOT NULL COMMENT '模型size参数',
  `usage_tokens` INT DEFAULT NULL,
  `cost_amount` DECIMAL(10,4) DEFAULT NULL COMMENT '成本快照(元)',
  `duration_ms` INT DEFAULT NULL,
  `moderation_status` TINYINT NOT NULL DEFAULT 0 COMMENT '0未审/1通过/2拒绝',
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '1正常/0用户已删',
  `order_id` INT DEFAULT NULL COMMENT '转打印订单后回填',
  `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY `uk_gen_token` (`token`),
  KEY `idx_gen_account` (`account_id`, `created_at`),
  KEY `idx_gen_created` (`created_at`),
  KEY `idx_gen_order` (`order_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='AI 图片生成记录';
```

说明：不把生成图硬塞进 `file_info`——`file_info.order_id NOT NULL` 且上传逻辑强绑订单（`FileInfoController.uploadFile` 校验 orderId），生成图在用户下单前没有订单，独立记录表更干净；转订单后只回填 `order_id` 做溯源，打印时走的仍是"createOrder → fileApi.upload(orderId)"既有主链路。

## 5. P0 功能详细设计

### 5.1 F1：AI 图片生成核心接口

#### 5.1.1 photo-service 侧（纯模型适配器，约 0.5 天）

新增两个文件，遵循 `change_bg.py` 的代码风格：

**`app/services/image_generation_service.py`**
- 用 `urllib`（对齐 chat-service `deepseek.py` 的做法，不引入新依赖）POST `{IMAGE_API_BASE_URL}/images/generations`，Header 带 `Authorization: Bearer {IMAGE_API_KEY}`；
- 入参 `model / prompt / size / response_format`；`model` 必须在 `IMAGE_MODEL_CATALOG` 内，否则 400；
- `IMAGE_API_KEY` 为空抛 503（语义与 Baidu OCR 一致：未配置不伪造成功）；
- 超时用 `IMAGE_API_TIMEOUT_SECONDS`；返回统一 `(b64, width, height, usage_tokens, duration_ms)`；
- 记录本次 model、usage、耗时到日志（photo-service metrics 自动覆盖请求层指标）。

**`app/api/v1/generate_image.py`**
- `POST /api/photo/image-generate`（依赖 `get_current_user`，JWT 校验）：body `{model, prompt, size, watermark_text?}`；prompt 长度校验 ≤ 500；
- `GET /api/photo/image-models`：返回 `IMAGE_MODEL_CATALOG`（含各模型 size 预设列表，hy-image-v3 的 37 组尺寸在联调第 1 步确认格式后填入 catalog 的 `sizes` 字段）；
- `app/main.py` 按现有双前缀注册：`app.include_router(generate_image.router, prefix="/api/photo", tags=["图片生成"])`（`/api/v1` 前缀可同注册，与 change_bg 保持一致）。

#### 5.1.2 print-service 侧（业务编排，约 1.5 天）

新增包 `com.example.printshop.imagegen`，镜像 `ocr` 包结构：


`ImageGenController` 接口契约：

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/imagegen/generate` | 登录用户/管理员 | 生成一张图 |
| GET | `/api/imagegen/models` | 登录用户/管理员 | 代理 photo 模型目录 |
| GET | `/api/imagegen/templates` | 登录用户/管理员 | 模板列表（status=1） |
| POST | `/api/imagegen/polish` | 登录用户/管理员 | prompt 润色（F4） |
| GET | `/api/imagegen/records?page=&size=` | 登录用户（本人） | 我的作品分页 |
| DELETE | `/api/imagegen/records/{id}` | 登录用户（本人）/ `photo:imagegen:manage` | 软删 |
| GET | `/api/imagegen/download/{ownerId}/{token}` | JWT + owner 或管理员 | 镜像 OCR 下载校验 |
| GET | `/api/imagegen/config` | `photo:imagegen:manage` | 读运营配置 |
| PUT | `/api/imagegen/config` | `photo:imagegen:manage` | 改配置 + 写审计 |
| GET | `/api/imagegen/usage?start=&end=` | `photo:imagegen:query` | 成本/用量统计 |
| GET | `/api/imagegen/records/all?...` | `photo:imagegen:query` | 全量记录（管理端） |

`POST /api/imagegen/generate` 请求/响应示例：

```jsonc
// 请求
{ "model": "seedream-image-v5.0-lite", "prompt": "大学社团招新海报…",
  "size": "1242x1660", "templateKey": "poster_club", "polish": true }
// 成功响应 data
{ "id": 123, "token": "uuid", "model": "...", "width": 1242, "height": 1660,
  "downloadUrl": "/api/print/imagegen/download/7/uuid", "previewUrl": "data:image/png;base64,...",
  "costAmount": 0.22, "quotaRemaining": 3, "polished": true }
```

- `previewUrl` 直接回 b64 data URL（本次会话内即显即用，不再二次请求）；持久化与再获取一律走 downloadUrl（JWT blob 下载，前端参照 `client/views/Ocr.vue` 的 `download` 实现）。
- 失败语义：Key 未配/功能关停 → 503；配额超限 → 429（`message` 含剩余配额与重置时间）；审核拒绝 → 422 并记 `moderation_status=2`；photo-service 熔断/超时 → 504 语义透传，**不重试**（每张都花钱，重试由用户手动触发）。

`ImageGenService.generate` 编排顺序（每步失败即短路）：

1. `ImageGenSettingsService` 读配置：`enabled=false` → 503；
2. prompt 清洗：去首尾空白、长度 ≤ `max_prompt_length`、本地敏感词黑名单校验（词表放 `printshop.imagegen.prompt-blocklist` 配置，逗号分隔，命中 → 422）；
3. `ImageGenQuotaService.tryConsume(accountId)`：Redis key `imagegen:quota:{accountId}:{yyyyMMdd}`，`INCR` 后首次 `EXPIRE 172800`；≥ `daily_quota_per_user` → 429；
4. 全平台成本熔断：`SELECT COALESCE(SUM(cost_amount),0) FROM image_gen_record WHERE created_at>=CURDATE()` 超 `daily_cost_cap` → 503 + 写 SECURITY_ALERT 日志（复用 `SecurityAlertService`）；该查询每分钟最多执行一次（本地缓存），避免每次生成都全表扫；
5. `model_id` 白名单校验（对照 models 目录缓存）；
6. `polish=true` 且 `polish_enabled` → `DeepSeekPolishService.polish(prompt)`，润色结果同样过第 2 步校验；润色失败降级用原 prompt（不阻塞生成）；
7. `imageGenRestTemplate` 携带用户 `Authorization` 头调 photo-service `/api/photo/image-generate`；
8. 审核开关开 → `ImageContentModerationService.moderate`（把返回的 b64 解码包成 `MockMultipartFile` 传入，复用其 fail-closed 语义；该服务 endpoint 未配置时按其既有行为跳过，不额外阻断）；
9. `ImageGenStorageService` 写 `data/files/imagegen/{accountId}/{token}.png`（路径归一化校验对齐 `FileInfoController` 的 `dest.startsWith(uploadDir)` 防穿越写法）；
10. 写 `image_gen_record`（含 usage、cost 快照、duration、moderation_status=1）；
11. 返回记录 + `quotaRemaining`。

### 5.2 F2：生成图一键转打印订单（闭环）

## 7. 管理体系与运维（基于现有体系，不新造轮子）

### 7.1 权限（RBAC）

- 权限点 2 个：`photo:imagegen:manage`（配置/删除他人记录/模板管理）、`photo:imagegen:query`（记录与台账查看）；
- 用户端生成不设权限点——登录用户即可，量控靠配额（与"文件上传用 requireAdmin/requireUser 而非权限点"的既有取舍一致，见 AGENTS.md 9.4）；
- `role_key=superadmin` 代码级直通不受影响；菜单变更后管理员重新登录即生效（permissions 随 `AuthInterceptor` 一次查库装载）。

### 7.2 运营配置与审计

- 一切可调项收敛在 `image_gen_settings` 单行表（第 3.2 节），管理端修改必须留审计（`image_gen_setting_audits`），与 chat_settings 审计同构，答辩与排查时可直接回答"谁在什么时候改了配额"；
- 配置读取带 60s 进程内缓存，改配置后最迟 60s 生效（打印平台场景可接受，避免每次生成都查库）。

### 7.3 配额与限流（三层防线）

| 层 | 机制 | 参数来源 |
|---|---|---|
| Gateway | 既有 600/min/IP+路由组 IP 限流 | 不改 |
| print-service | Redis 日配额 `imagegen:quota:{accountId}:{yyyyMMdd}` | `daily_quota_per_user`（默认 5 张/天） |
| print-service | 全平台日成本熔断 | `daily_cost_cap`（默认 50 元/天），超限 503 + SECURITY_ALERT |

成本熔断是防刷的最后闸门：即使配额被多账号绕过，单日平台支出有硬上限。恢复方式为次日自动（查询窗口为当日）或管理员调高 cap。

### 7.4 内容安全

1. prompt：长度上限 + 本地黑名单词表（`printshop.imagegen.prompt-blocklist`）；
2. 生成图：`ImageContentModerationService` 审核后落盘，`moderation_enabled` 生产恒开（该服务 fail-closed 语义既有）；审核拒绝记录保留（`moderation_status=2`），管理端可查——既是安全审计也是误杀申诉依据；
3. 水印脚注（hy-image-v3 `watermark_text`）默认关，运营可开，用于付费打印图的防盗印溯源；
4. 合规红线写入本方案与后续 AGENTS.md：不提供去水印/去 logo/换脸能力，prompt 黑名单覆盖相关关键词。

### 7.5 成本核算

- 每条记录快照 `usage_tokens / cost_amount / duration_ms / model_id`，单价来自调用时刻 catalog；
- 台账口径：`GET /api/imagegen/usage` 按日按模型聚合；对账时与 TokenHub 控制台账单核对（价格漂移由快照隔离）；
- photo-service 请求层 metrics（QPS/状态码/耗时）继续覆盖新端点，无需额外埋点；print-service 在 generate 成功/失败路径打 INFO/WARN 日志（含 accountId、model、duration、cost），对齐现有审计日志规范。

### 7.6 故障与降级

| 故障 | 行为 |
|---|---|
| `IMAGE_API_KEY` 未配 | photo-service 503，前端生成按钮置灰并提示"未开通" |
| photo-service 熔断/宕机 | Gateway FallbackController 既有降级响应；print-service 不重试（避免双倍计费） |
| DeepSeek 未配/失败 | 润色 503/降级用原 prompt，生成主链路不受影响 |
| 审核服务不可用 | fail-closed（拒绝生成），管理端可见失败记录 |
| Redis 不可用 | 配额检查失败按 fail-closed 拒绝生成（打印平台已有 Redis 强依赖，语义一致） |

### 7.7 例行维护

- `image_gen_record` 按月归档（数据量 = 生成张数，毕设量级可不管，写明即可）；`data/files/imagegen` 磁盘占用随"软删即删文件"自清；
- 上线首周每天看一次 usage 台账核对成本与配额命中情况，之后随生产 smoke 例行；
- `legacy_print_compat_audit.py` 不受影响（新增路径都在 `/api/print/**` 规范前缀内）。
